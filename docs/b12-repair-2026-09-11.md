## Changes

[Boundary.cs](../sources/Video/Internal/Boundary.cs) parses the HTTP Content-Type
field with the framework's
[MediaTypeHeaderValue.TryParse](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.headers.mediatypeheadervalue.tryparse).
Media types and parameter names are compared without regard to case, while the
boundary value retains its case. Separate parameters, surrounding whitespace,
quoted values, and quoted-pair escapes no longer corrupt that value. Legacy
response line folding is unfolded before parsing, following
[RFC 9112 section 5.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-5.2).
Bare line breaks remain invalid.

Accepted media types are `multipart/x-mixed-replace`, `multipart/mixed`, and
`application/octet-stream`. Missing or empty multipart boundaries retain the
existing empty-boundary behavior; octet streams also use an empty boundary.
Unsupported types, malformed headers, duplicate boundary parameters, and boundary
parameters without a value produce ArgumentException. A missing response produces
ArgumentNullException. The existing camera boundary-prefix correction remains.
This resolves both original MIME failures: mixed-case names and trailing parameters.

[MJPEGStreamParser.cs](../sources/Video/Internal/MJPEGStreamParser.cs) retains
the final `markerLength - 1` bytes after an unsuccessful search. The marker is the
JPEG header while seeking a frame start, the multipart boundary while seeking its
end, or the next JPEG header for raw streams. Search positions stay nonnegative,
and raw streams wait for enough bytes to search their actual delimiter.
This resolves the three original failures with one-, two-, and three-byte reads
and also handles short boundaries and split headers in raw streams.

Public signatures are unchanged. Source changes stay in the two primary class
files. Raw frames still end at the next JPEG header: EOF alone does not emit the
last frame. Existing fixed buffer capacity and image-decoder behavior are outside
this marker/parameter repair.
